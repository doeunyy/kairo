2-1. 하이브리드 LLM 라우터 (router/)

STAR

S
과제는 클라우드 LLM과 로컬 Gemma를 작업 성격에 따라 나눠 써야 하는데, Hermes v0.21.5에는 라우팅 기능이 없습니다.
T
Hermes를 고치지 않고 요청마다 모델을 고르는 중간 서버를 만들되, 민감한 요청은 절대 클라우드로 가지 않게 해야 했습니다.
A
Hermes가 ChatGPT로 보내는 요청을 받는 프록시를 Starlette로 만들고, 요청에서 특징을 뽑아 순서가 정해진 규칙으로 판단하게 했습니다.
R
클라우드·로컬 모두 tool call 성공, 429 대체, 노트북 오프라인 시 보류를 실제로 확인했습니다. 테스트 23개 통과.

기술 상세

  • 연결 방식: Hermes 공식 환경변수 HERMES_CODEX_BASE_URL을 라우터 주소로 지정합니다. Hermes는 원래 ChatGPT로 보낼 Responses API 요청(store:false, SSE 스트림)을 라우터로 보냅니다.
  • 특징 추출: 사용자 메시지 첫 줄의 <!--route task=… privacy=high reasoning=high--> 태그를 먼저 봅니다. 태그가 없으면 단어 목록(연봉·salary → privacy, 비교·분석·jd → reasoning)으로 판단하고, 토큰은 글자 수 ÷ 3으로 추정합니다.
  • 판단 규칙(위에서부터 처음 맞는 것):
    1. privacy high → 노트북이 살아 있으면 local, 아니면 hold(클라우드로 보내지 않음, fail-closed)
    2. rate limit 중 → 로컬 가능하면 local
    3. 40K 토큰 초과 → cloud (long_context)
    4. reasoning high → cloud
    5. 태그 없는 8K 초과 → cloud (agentic_prompt)
    6. 짧은 요청 → local (simple_task), 나머지 → cloud (default)
  • 클라우드 경로: 요청 본문을 그대로 넘기고, Hermes가 붙인 OAuth Bearer 토큰도 그대로 전달합니다(pass-through). Hermes는 공식 주소로 보낼 때만 계정 헤더를 붙이므로, 라우터가 JWT에서 ChatGPT-Account-ID를 읽어 헤더를 다시 붙입니다. 라우터는 로그인 정보를 저장하거나 갱신하지 않습니다.
  • 로컬 경로: 모델명을 Gemma로 바꾸고, Codex 전용 필드(include, prompt_cache_key, 암호화된 reasoning 항목)를 지운 뒤 reasoning.effort=none을 넣습니다. type:function 도구만 남기고 Ollama /v1/responses로 보냅니다.
  • 실패 처리: 클라우드가 실패(429 등)하고 로컬이 가능하면 한 번 로컬로 재시도합니다. 로컬 실패는 클라우드로 재시도하지 않습니다(민감 정보 보호). 429가 나면 일정 시간 로컬로 보내고, 플래그 파일 하나로 429를 흉내 내거나 해제할 수 있습니다.
  • 로그: 판단 하나당 JSONL 한 줄(경로, 이유, 특징, 상태, 결과, 지연시간)을 남깁니다. 스트림 속 response.completed/failed 이벤트로 성공·실패를 기록합니다.
  • 이유: 라우팅을 Hermes 밖에 두면 Hermes를 고칠 필요가 없고, 라우팅만 따로 테스트할 수 있습니다. Hermes 세션 기록은 실제로 답한 모델을 알려 주지 못하므로, 라우터 로그가 그 근거가 됩니다.

쉬운 설명

라우터는 우체국의 분류 직원입니다. 편지(요청)마다 “비밀 편지인지, 어려운 편지인지, 짧은 편지인지”를 보고 본사(ChatGPT)로 보낼지 동네 지점(노트북 Gemma)으로 보낼지 정합니다. 비밀 편지는 동네 지점이 문을 닫았으면 본사로 보내지 않고 보관합니다. 누가 처리했는지는 장부에 한 줄씩 적습니다.

2-2. 결정론적 메일 파이프라인 (core/)

STAR

S
채용 메일은 외부에서 오는 신뢰할 수 없는 글이라, 숨은 지시(prompt injection)가 들어 있을 수 있습니다.
T
LLM이 메일을 읽더라도 Notion 상태를 마음대로 바꾸거나 메일을 보낼 수 없게 해야 했습니다.
A
LLM은 정해진 JSON 칸 채우기만 하고, 어떤 지원 건인지와 어떤 상태로 바꿀지는 코드가 정하도록 역할을 나눴습니다.
R
합성 메일 5통이 기대대로 처리됐습니다: 상태 변경 2, 지원 건 질문 1, 발신자 차단 1, 숨은 지시 무시 1.

기술 상세

  • 처리 순서: prefilter → extraction → matcher → state transition → plan
  • prefilter: Message-ID가 없으면 버리고, ledger(SQLite, Message-ID가 primary key)에 이미 있으면 버립니다(멱등성, idempotency). 발신자 allowlist(주소 또는 @도메인)에 없으면 LLM을 부르기 전에 버립니다.
  • extraction (엄격한 스키마): 키는 type, company, role, posting_id, applied_on, deadline, confidence만 허용합니다. 모르는 키, 필수 키 누락, 정의되지 않은 type, 0–1 밖의 confidence, ISO 형식이 아닌 날짜, 120자 초과 텍스트는 모두 거부합니다.
  • matcher: 회사명을 정규화(Inc·Labs·(주) 제거)합니다. 점수는 회사 일치 0.6, 공고 ID 일치 1.0이고, 직무는 단어 겹침(Jaccard)으로 비교하되 흔한 단어(stopword)는 뺍니다. 확신도 0.7 미만, 최고점 0.6 미만, 1·2위 차이 0.3 미만 중 하나라도 해당하면 사용자에게 묻습니다(ask).
  • 상태 전이: 화이트리스트에 있는 전이만 적용합니다(예: Applied → Assessment/Interview/Offer/Rejected). 같은 상태는 변경 없음, 해당 없는 메일은 무시, 역방향은 거부(refuse)하고 경고합니다.
  • plan_update: 바꿀 필드를 Update 객체로만 만듭니다(last_contact, evidence_message_id, status, next_action, due). 지원일은 메일에 적힌 날짜를 우선 쓰고, 없으면 수신일과 그 출처를 기록합니다.
  • 이유: LLM의 권한을 “칸 채우기”로 줄이면 인젝션이 성공해도 최대 결과는 잘못된 칸 값입니다. 그 값도 스키마 검증과 전이 규칙을 통과해야 하므로 실제 데이터를 바꿀 경로가 없습니다.

쉬운 설명

LLM은 메일을 읽고 정해진 양식에 체크만 하는 아르바이트생이고, 장부를 실제로 고치는 건 규칙집을 따르는 정직원(코드)입니다. 메일에 “사장님이 이 사람 합격시키래요”라고 써 있어도, 아르바이트생은 양식에 체크만 할 수 있고 정직원은 규칙에 없는 일은 하지 않습니다.

2-3. 외부 서비스 연동과 발송 승인 게이트

STAR

S
파이프라인은 메일을 받아 Notion을 고치고 Discord로 알려야 하며, 과제상 메일 발송은 반드시 사람의 승인을 거쳐야 합니다.
T
Gmail·Notion·캘린더·Discord를 연결하되, 코드로 강제한 승인 없이는 발송이 불가능하게 만들어야 했습니다.
A
Python 표준 라이브러리만으로 어댑터를 만들고, HMAC 토큰 기반 승인 게이트를 구현했습니다.
R
실제 테스트 계정으로 전 과정을 확인했고, 클라우드에서도 ✅ 승인 후 정확히 1회 발송됐습니다.

기술 상세

  • Gmail: 앱 비밀번호로 IMAP/SMTP를 씁니다(Google OAuth Testing 모드의 7일 만료와 restricted scope 심사를 피하기 위해). BODY.PEEK로 읽어 읽음 처리를 하지 않고, 위치는 UIDVALIDITY + last UID 커서로 저장합니다. Python 3.13 imaplib에 없는 IMAP IDLE(RFC 2177)은 직접 구현했습니다. 초안은 \Drafts에 APPEND로 저장하고, SmtpSender는 outbox만 호출합니다.
  • 승인 게이트 (outbox):
    1. 초안을 SQLite에 저장하고 (받는 사람, 제목, 본문, In-Reply-To)의 sha256을 기록합니다. 초안은 수정할 수 없고(immutable), 받는 사람이 allowlist 밖이면 이 단계에서 거부합니다.
    2. Discord 미리보기 embed footer에 해시를 표시합니다.
    3. allowlist의 숫자 user ID가 ✅를 달고, 미리보기 해시가 저장된 해시와 같으면 HMAC-SHA256 토큰(초안·해시·승인자·만료 15분)을 발급합니다.
    4. send()에서 서명, 만료, 승인자, 받는 사람 allowlist를 다시 확인합니다.
    5. 조건부 UPDATE로 approved → sending을 선점해 토큰을 한 번만 쓰게 하고(single-use), SMTP가 실패하면 send_failed로 남기며 재시도하지 않습니다.
    6. 감사 로그에는 본문 없이 누가·언제·누구에게만 남깁니다.
  • Notion: 부모 페이지 아래에 DB를 자동으로 찾거나 만들고(캐시 → 하위 블록 검색 → 생성), 스키마에 새 필드가 생기면 추가합니다. 쓰기 직전에 다시 읽어 agent_rev와 last_edited_time을 비교하고(낙관적 동시성 제어), 다르면 RevConflict로 쓰지 않고 경고합니다.
  • 캘린더: RFC 5545 ICS를 직접 파싱합니다(line folding, TZID·UTC·종일 일정, DAILY/WEEKLY와 INTERVAL·COUNT·UNTIL·BYDAY·EXDATE·RECURRENCE-ID). 서머타임이 바뀌어도 반복 일정의 시각을 유지하고, 빈 시간은 일정 앞뒤 15분 여유를 두고 계산합니다.
  • Discord: REST만 씁니다(gateway는 Hermes 담당). 모든 게시글에 allowed_mentions: {parse: []}를 넣어 메일 내용이 멘션을 일으키지 못하게 하고, 승인은 반응 사용자 목록을 polling해서 처리합니다.
  • extractor: 메일 분석 요청은 라우터에 privacy=high로 보내 로컬 Gemma에서만 처리합니다. 본문의 <!--는 무력화해 라우팅 태그 주입을 막습니다.
  • 이유: 표준 라이브러리만 쓰면 의존성(공급망 공격 표면)이 줄고, 모든 외부 호출을 fake로 바꿔 테스트할 수 있습니다.

쉬운 설명

메일 발송을 은행 송금처럼 만들었습니다. Kairo는 송금 신청서(초안)만 쓸 수 있고, 주인이 Discord에서 ✅ 도장을 찍어야 보낼 수 있습니다. 도장은 그 신청서 한 장에, 15분 동안, 한 번만 쓸 수 있습니다. 받는 사람이 허용 목록에 없으면 도장이 있어도 보내지 않습니다. Notion을 고칠 때는 “내가 마지막으로 본 버전이 맞나?”를 확인해서, 그사이 누가 고쳤으면 덮어쓰지 않습니다.

2-4. Hermes 연동 (MCP 서버, 스킬, SOUL, Discord, 도구 차단)

STAR

S
만든 기능을 Hermes 에이전트가 대화 중에 써야 하고, 과제는 스킬 4개 이상을 요구합니다.
T
필요한 능력은 주되, 위험한 능력(발송, 상태 변경, 셸 접근)은 구조적으로 막아야 했습니다.
A
Kairo 기능을 MCP 서버로 노출하고 Hermes 기본 도구 중 위험한 것을 껐습니다.
R
Discord 대화에서 실제 Notion·메일·캘린더 데이터로 정확히 답했고, 초안 → ✅ → 발송까지 동작했습니다.

기술 상세

  • MCP 서버: Hermes mcp_servers 설정으로 stdio MCP 서버(MCP SDK 2.x MCPServer)를 붙였습니다. 도구 9개:
    • 읽기 전용(readOnlyHint): list_applications, recent_mail, calendar_events, free_slots, check_conflict, weather, draft_status
    • 쓰기: add_application(Interested/Preparing으로만 생성), draft_email
    발송·상태 변경·승인 도구는 존재하지 않습니다. 프롬프트로 금지한 것이 아니라 아예 만들지 않았습니다.
  • recent_mail: 원장의 mail_index에서 헤더와 검증된 필드만 주고 본문은 주지 않습니다. 라우터는 마지막 사용자 메시지만 보고 판단하므로, 도구 결과의 메일 본문이 클라우드 모델로 새는 것을 원천적으로 막기 위해서입니다.
  • 도구 차단 (agent.disabled_toolsets): terminal, file, code_execution, browser, delegation, discord(raw), discord_admin 등 17종을 꺼서, 모델이 kairo.env·승인 키·로그인 파일을 읽지 못하게 했습니다(최소 권한, least privilege).
  • 실행기 (launch.py): Hermes 프로세스에는 DISCORD_*, HERMES_*, API_SERVER_*만 넘깁니다. 메일·Notion 비밀값은 MCP 서버가 kairo.env에서 직접 읽습니다.
  • 스킬 4개: job-tracker, recruiting-email, interview-scheduling, interview-weather. 각 SKILL.md에 When to Use, Quick Reference, Procedure, Pitfalls, Verification을 적고, requires_toolsets: [mcp-kairo]를 걸었습니다.
  • SOUL.md: 가상 사용자 Emily Kim, 영어 출력, 한국어 용어 사전(지원 = application), 도구 사용 규칙과 금지 규칙.
  • Discord: Hermes가 gateway로 연결하고, DISCORD_ALLOWED_USERS(숫자 ID)와 ALLOWED_CHANNELS로 #kairo에서만 응답합니다.
  • 이유: MCP는 Hermes 공식 확장 방식이라 Hermes를 고칠 필요가 없고, 도구 목록 자체가 권한 경계가 됩니다.

쉬운 설명

Hermes는 일을 잘하는 비서인데, 이 비서에게 “Kairo 서랍”(MCP)만 열어 주고 회사 금고(셸, 파일, 비밀번호)는 잠갔습니다. 서랍에는 장부 보기, 일정 보기, 편지 초안 쓰기 도구는 있지만 “편지 보내기” 도구는 아예 없습니다. SOUL.md는 업무 수칙, 스킬은 업무 매뉴얼입니다.

2-5. 능동형 동작 (메일 감시, cron 6종, 조용한 시간)

STAR

S
과제는 묻기 전에 먼저 움직이는 비서를 요구합니다. 수동으로만 실행되는 기능은 부분 점수입니다.
T
메일이 오면 바로 처리하고, 정해진 시각에 브리핑과 점검을 하되, 밤에는 방해하지 않아야 했습니다.
A
IMAP IDLE 기반 감시 프로세스와 Hermes cron 6개를 만들고, 조용한 시간과 sweep 잠금을 넣었습니다.
R
메일 도착 27초 안에 Notion 반영과 Discord 알림이 왔고, 아침 브리핑과 하루 마무리는 즉시 실행으로 전달을 확인했습니다.

기술 상세

  • 메일 감시 (watch): IDLE로 60초 단위로 기다리다 EXISTS 알림을 받으면 바로 처리합니다. 기다리는 사이 ✅ 반응도 확인합니다. IDLE이 놓친 메일은 15분 cron이 다시 처리하고, 둘은 fcntl.flock을 공유해 동시에 돌지 않습니다.
  • cron (America/Los_Angeles):
    • 아침 브리핑 08:00, 하루 마무리 21:00, 후속 점검 12:00: agent + script. 스크립트가 결정론적 데이터를 프롬프트에 넣고, 모델은 그걸로 문장만 씁니다. 후속 점검은 할 일이 없으면 [SILENT].
    • 면접 임박 5분마다, 백업 메일 처리 15분마다: no-agent script. 모델 호출 없이 비용 0, 결과가 항상 같습니다.
    • 메모리 정리 03:00: agent, 결과는 로컬에만 남김.
  • 스크립트 위치: Hermes는 $HERMES_HOME/scripts 안의 스크립트만 실행하므로(심볼릭 링크 거부) install.sh가 래퍼를 복사합니다.
  • 조용한 시간 (22:00–07:30): 알림을 deferred 큐에 넣었다가 아침 브리핑에 한 번만 포함합니다. 12시간 안의 마감은 바로 보내고, 미룬 이유를 로그에 남깁니다.
  • 실행 원장: Hermes cron이 “놓친 실행은 재시작 후 1회만 보충, tick마다 잠금”을 이미 보장해서 그대로 썼습니다.
  • 이유: 메일은 이벤트 기반(IDLE)이 가장 빠르고, 예약 작업은 Hermes cron이 중복 방지와 보충 실행을 이미 해 줍니다.

쉬운 설명

우편함 앞에서 계속 기다리는 직원이 있어서 편지가 오면 바로 처리합니다. 혹시 놓칠까 봐 15분마다 우편함을 한 번 더 확인하는 순찰도 있습니다. 두 사람이 같은 편지를 동시에 처리하지 않도록 열쇠 하나를 돌려 쓰고, 밤에는 급하지 않은 소식은 아침에 한꺼번에 알려 줍니다.

2-6. 클라우드 배포 (Cloud Run Instance, Tailscale, Secret Manager, 스냅샷)

STAR

S
비서는 클라우드에서 상시 동작해야 하는데, Gemma는 노트북에 있습니다.
T
클라우드와 노트북을 안전하게 연결하고, 비밀값은 Secret Manager에 두고, 재시작해도 상태가 유지되게 해야 했습니다.
A
컨테이너 이미지, 10단계 entrypoint, GCP 설정 스크립트, 스냅샷 모듈을 만들어 us-west1에 배포했습니다.
R
기동 약 80초. 두 추론 경로, fail-closed, HTTPS 키 검사(키 없으면 401), 메일 처리, Discord 대화, 승인 발송을 클라우드에서 모두 확인했습니다.

기술 상세

  • 이미지:
    • 기반은 python:3.13-slim-trixie(SQLite 3.46)입니다.
    • 버전 고정: Hermes 태그와 커밋 해시(다르면 빌드 실패), Tailscale 1.104.5, uv 0.13.1, uv sync --frozen. 바이트코드는 빌드 때 미리 컴파일합니다.
    • 코드는 root 소유 읽기 전용, 실행은 uid 1000. tini가 PID 1을 맡아 신호를 전달합니다.
  • GCP: API 6개, Artifact Registry, 비공개 버킷(공개 접근 차단, 버킷 단위 통합 권한), 런타임 서비스 계정. 서비스 계정 권한은 버킷 objectUser, 시크릿 3개 읽기, 로그인 시크릿 하나에만 새 버전 추가뿐이고 프로젝트 전체 역할은 없습니다.
  • 비밀값: kairo-env(노트북 전용 줄 제외), kairo-chatgpt-auth, kairo-approval-key(32바이트)를 읽기 전용 파일로 마운트합니다. ChatGPT 로그인은 노트북과 별도입니다. refresh token은 한 번 쓰면 바뀌고 재사용이 감지되면 계열 전체가 무효가 되므로, 공유하면 한쪽이 갱신하는 순간 다른 쪽이 끊깁니다.
  • entrypoint:
    1. 필수 키 확인
    2. 버킷 쓰기 검사
    3. 스냅샷 복원(설정은 이미지, 로그인은 Secret Manager에서)
    4. 격리 리포트
    5. tailscaled(userspace 모드, SOCKS5 :1055, 일회성 태그 키)
    6. 라우터(socks5h://로 노트북 tailnet IP 접속)
    7. Hermes 게이트웨이(Discord, $PORT의 API 서버, 키 필수)
    8. Discord 연결 확인 후 메일 감시
    9. cron 등록(백그라운드)
    10. 준비 확인 후 15분 백업 루프·5분 로그인 동기화. SIGTERM이 오면 마지막 백업 후 종료
  • 스냅샷: SQLite는 FUSE 위에서 잠금과 원자적 rename이 안 돼서 로컬 디스크에 둡니다. SQLite online backup API로 일관된 복사본을 tar.gz로 버킷에 저장하고(최근 8개), 비밀값 파일은 빼며, 복원할 때 경로 탈출을 막습니다.
  • 로그인 write-back: auth.json 해시가 바뀌면 메타데이터 서버 토큰으로 Secret Manager addVersion을 호출합니다. 다음 기동은 그 최신 버전을 씁니다.
  • 배포 설정: 1 vCPU / 1 GiB, 재시작 정책 always, GCS FUSE(uid=1000;file-mode=600;dir-mode=700), TCP startup probe, HTTPS URL은 API 서버만 노출.
  • 이유: 과제 문서의 권장 경로(Setup §2.9 순서, userspace Tailscale, Secret Manager)를 그대로 따랐고, 각 단계를 실패 즉시 멈추게(fail-fast) 만들어 잘못된 상태로 동작하지 않게 했습니다.

쉬운 설명

Kairo를 클라우드의 작은 사무실로 옮겼습니다. 열쇠는 금고(Secret Manager)에서 꺼내 쓰고, 노트북의 Gemma와는 둘만 아는 비밀 통로(Tailscale)로 연결했습니다. 통로는 Gemma 창구(11434번) 하나에만 열려 있습니다. 사무실은 언제든 닫았다 다시 열 수 있으니, 15분마다 장부 사본을 창고(버킷)에 맡기고, 다시 열 때 그 사본을 펼칩니다.

2-7. 운영 안정성: heartbeat · 단계적 복구 · 계획 재시작 (8단계)

STAR

S
48시간 동안 사람이 지켜보지 않아도 돌아가야 합니다. 그 사이 노트북이 꺼지거나, Tailscale 터널이 끊기거나, 프로세스가 죽을 수 있습니다. 과제는 heartbeat, 복구, 재시작 후 상태 유지를 증거와 함께 요구합니다.
T
장애 원인을 구분해서 고칠 수 있는 것만 자동으로 고치고, 고칠 수 없는 것은 알리기만 해야 했습니다. 재시작이 반복되는 상황(restart loop)도 막아야 했습니다. 정기 재시작 뒤에는 메모리, cron, 처리 기록이 그대로 남아 있어야 합니다.
A
컨테이너 안에 supervisor 프로세스를 추가했습니다. 상태 판정과 복구 결정은 테스트할 수 있는 순수 함수(state machine)로 만들고, 장애를 일부러 일으켜 실제 클라우드에서 검증했습니다.
R
계획 재시작은 69초 만에 ready로 돌아왔고, 메모리·cron·처리 기록이 모두 유지됐습니다. 노트북 오프라인과 터널 장애 두 시나리오 모두 의도한 단계대로 반응했습니다. supervisor 테스트 6개를 추가했습니다(core 69개).

기술 상세

  • heartbeat (기본 5분, KAIRO_HEARTBEAT_EVERY_S): 매번 라우터 /router/health를 호출합니다. 이 엔드포인트는 캐시를 쓰지 않고 SOCKS5 → tailnet → 노트북 /api/tags를 새로 확인합니다. 동시에 tailscale status --json에서 노트북 peer의 Online 값을 읽습니다.
  • 상태 분류 (classify): 두 신호를 조합해 다섯 가지로 나눕니다.
    • ok: 모델에 닿음
    • laptop_offline: peer가 오프라인. 클라우드에서 고칠 수 없음
    • model_missing / http_error: Ollama는 응답했지만 쓸 수 없음. 네트워크를 재시작해도 소용없음
    • transport: 노트북은 온라인인데 연결이 안 됨. 터널 문제일 가능성이 높아 유일한 자동 복구 대상
  • 단계적 복구 (Policy.step):
    1. transport가 연속 3회면 1단계: tailscale down → up(일회성 태그 키)으로 tailscaled 프로세스는 그대로 두고 연결만 다시 맺은 뒤 재검증합니다.
    2. 연속 6회면 2단계: supervisor가 exit 3으로 끝나고, entrypoint가 백업 후 exit 1 → 재시작 정책 always로 Cloud Run이 새 컨테이너를 띄웁니다.
    3. 2단계는 1시간에 최대 1회입니다. 마지막 복구 재시작 시각을 버킷(lifecycle/last_recovery_restart)에 남겨, 새 컨테이너도 이 제한을 이어받습니다(restart loop 방지).
  • 알림: 원인과 관계없이 비정상이 3회 연속이면 Discord에 한 번 알리고(“민감 작업은 클라우드로 보내지 않고 보류 중”), 회복하면 한 번 더 알립니다.
  • 추론 확인: 정상일 때 6번째 beat(30분)마다 <!--route task=heartbeat simple=true--> 요청을 라우터에 보내, 연결 확인을 넘어 실제 Gemma 추론과 지연시간까지 기록합니다.
  • 계획 재시작: PT 00:30, 03:30 … 21:30(3시간 간격)이나 버킷 flags/restart_now가 있으면 exit 10으로 끝납니다. entrypoint는 wait -n -p로 어느 자식이 어떤 코드로 끝났는지 구분해, 계획 재시작은 로그인 동기화 → 스냅샷 → stop · planned_restart 기록 → exit 0으로 처리합니다. 같은 슬롯은 한 번만 실행하고, 기동 후 15분 안에는 하지 않습니다.
  • 증거 기록: 모든 이벤트(heartbeat, recovery_stage1_tailscale_reset, recovery_stage2_container_restart, planned_restart, inference_probe)를 stdout(Cloud Logging)과 버킷 lifecycle/heartbeat.jsonl에 JSON 한 줄씩 남기고, 기동·종료는 lifecycle/events.jsonl에 남깁니다.
  • 재시작 안전성 보강:
    • cron 등록 결과(added/skip)를 로그로 남겨 중복 등록이 없음을 증명합니다.
    • 메일 감시는 기동 즉시 sweep합니다. 다운타임 중 도착한 메일은 IDLE로는 알 수 없기 때문입니다.
    • 첫 배포에서는 기존 메일을 baseline으로만 기록합니다.
  • 이유: 고칠 수 없는 장애(노트북 꺼짐)에 재시작을 반복하면 비용만 들고 로그가 오염됩니다. 원인 판정과 결정 로직을 부수효과와 분리하면, 실제 장애를 기다리지 않고 단위 테스트로 모든 분기를 검증할 수 있습니다.
