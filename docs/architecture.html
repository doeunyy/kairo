3하이브리드 라우팅 정책

라우터는 요청마다 다음 순서로 판단하고, 결정·근거·결과를 한 줄 JSON으로 남깁니다. 작업 속성은 두 경로로 얻습니다. 스킬과 cron 프롬프트는 첫 줄에 태그를 붙이고(<!--route task=mail_extract privacy=high-->), 태그가 없는 자유 대화는 토큰 추정치와 민감어 사전(연봉, 개인 메모 등)으로 분류합니다.

  1. privacy=high → 로컬. 로컬이 불가능하면 클라우드로 보내지 않고 큐에 보류하고 “로컬 모델 오프라인, n건 대기”를 알립니다 (fail-closed).
  2. 클라우드 rate-limit 상태 (실제 429 또는 시뮬레이션 플래그, 쿨다운 10분) → 로컬. 근거는 rate_limit.
  3. 추정 입력 24K 토큰 초과 또는 reasoning=high → 클라우드.
  4. simple이고 로컬이 정상 → 로컬.
  5. 그 외 → 클라우드. 클라우드가 실패하면 비민감 작업만 로컬로 재시도하고 fallback_from을 기록합니다.

429 시뮬레이션 (되돌릴 수 있게)

버킷의 플래그 파일 /mnt/agent-state/flags/simulate_cloud_429가 있으면 라우터가 클라우드 호출 대신 합성 429를 만들고, 로그에 "simulated":true를 남깁니다. 지우면 다음 요청부터 원래대로 돌아갑니다. Telegram 관리자 명령 /rl on|off도 같은 파일을 씁니다. 실제 할당량은 쓰지 않습니다.

4핵심 플로우

4.1 새 채용 메일 처리 (이벤트 트리거)

  • 추출 스키마: {type: ack|assessment|interview_request|interview_confirmed|rejection|offer|newsletter|other, company, role, posting_id?, applied_on?, deadline?, confidence}
  • 매칭 규칙: 회사 + 직무 + 공고 ID/링크로 점수를 매깁니다. 후보가 하나이고 점수가 임계값 이상이면 자동 반영합니다. 같은 회사에 2건 이상이거나 점수가 낮으면 Telegram 인라인 버튼으로 묻습니다.
  • 날짜 규칙: 메일에 지원일이 적혀 있으면 그 날짜를 applied_on으로 쓰고, 없으면 수신일을 쓰되 date_source=received로 표시합니다.
  • 멱등성: 처리한 Message-ID를 원장(SQLite)과 Notion 속성에 함께 기록해서, 재시작이나 IDLE 재연결 뒤 같은 메일을 다시 반영하지 않습니다.
  • 백업 경로: IDLE이 끊겼을 때를 대비해 15분마다 cron이 미처리 메일을 점검합니다. cron 시각에 실행되는 polling은 event-driven으로 인정됩니다 (§2.4).

4.2 지원 상태 전이

Notion DB 속성: 회사 · 직무 · 공고 링크/ID · 상태 · 지원일(+출처) · 최근 연락일 · 다음 행동 · 기한 · 관련 Message-ID · 변경 근거 · JD 요약 · agent_rev(낙관적 동시성 검사용 수정 번호).

4.3 메일 발송 승인 (HITL)

  1. 모델에게 노출되는 도구는 draft_email뿐입니다. 발송 도구는 모델의 도구 목록에 아예 없습니다. 초안은 Drafts 폴더와 outbox 원장에 draft_id와 본문 해시를 함께 저장합니다.
  2. Telegram에 초안 미리보기와 [승인] [수정] [폐기] 버튼을 보냅니다.
  3. [승인] 콜백은 allowlist에 있는 숫자 user ID에서 와야 하고, 해시가 일치해야 합니다(그사이 수정되지 않았는지 확인). 통과하면 코드가 HMAC 승인 토큰을 발급합니다. 토큰 키는 모델이 접근할 수 없습니다.
  4. outbox.send(draft_id, token)는 토큰 검증 후 수신자 allowlist(테스트 계정 도메인과 주소)를 다시 확인하고, 통과해야만 SMTP로 보냅니다. 승인자, 시각, 수신자를 감사 로그에 남깁니다.
  5. cron 작업에는 승인 경로가 없습니다. 초안을 만들고 알림만 보내며, 기다리지 않습니다.

4.5 기동 · heartbeat · 복구 · 계획 재시작

기동 순서

  1. 시크릿 env 확인 (값은 로그에 남기지 않음)
  2. /mnt/agent-state 쓰기 검사, 실패하면 종료
  3. 최신 스냅샷을 HERMES_HOME으로 복원 후 restore_ok 기록
  4. 격리 리포트 출력: id, CapEff, 읽기 전용 경로, 열린 포트
  5. tailscaled → login → 라우터 → Hermes → watcher 순서로 기동
  6. 준비 확인: Telegram 응답, /api/tags에 모델 존재, 소형 추론 1회
  7. cron 등록이 중복 없는지 확인 후 ready 기록

heartbeat와 단계적 복구

  • 5분마다 SOCKS 경유 /api/tags 확인, 30분마다 실제 추론 1회
  • 전송 실패가 연속 3회면 tailscaled만 재시작한 뒤 재검증
  • 그래도 실패하면 컨테이너 재시작 (1시간에 최대 1회)
  • 모델 누락, HTTP 에러, 노트북 오프라인으로 확인된 경우는 네트워크를 재시작하지 않음
  • 3시간마다 계획 재시작: 00:30, 03:30, 06:30 … 21:30. 백업 후 planned_restart 기록 → 종료 → 플랫폼이 재기동 확인 필요 (안 되면 Cloud Scheduler로 stop/start)

동시 쓰기 전략

메모리 파일은 single-writer, 나머지는 append-only journal입니다. 메시지 핸들러, cron, watcher는 메모리를 직접 고치지 않고 자기 전용 journal 파일에 “학습 제안”만 추가합니다. 03:00 정리 작업만 USER.md와 MEMORY.md를 고칩니다. 사용자가 “기억해”라고 명시한 경우는 같은 writer 큐를 통해 즉시 반영합니다. FUSE에서 같은 파일에 여러 프로세스가 append하는 상황을 피하려고 파일을 writer별로 나눴습니다.

Hermes 백그라운드 writer 끄기

auxiliary.background_review.enabled: false, memory.nudge_interval: 0. 메일 내용이 인젝션 방어 밖에서 메모리에 기록되는 경로를 막습니다 (Ref §6.2). Notion은 agent_rev를 비교한 뒤 쓰는 version-aware 방식입니다.

영속성 테스트: “내 테스트 프로젝트 이름은 Project Cardinal” → 스냅샷이 생성됐는지 로그로 확인 → stop/start → 새 대화에서 다시 질문 → 복원 로그와 답변을 함께 캡처합니다.

① 컨테이너 격리 (필수) ② 권한 범위 제한: 발송 게이트 · 전이 규칙 ③ 자격증명 관리: Secret Manager ④ 프롬프트 인젝션 방어 + 공격 3건 이상

최소 요건은 2개지만 4개를 모두 주장합니다. 컨테이너 격리 증거는 non-root uid 1000, 불필요한 capability 제거, 이미지에 시크릿 없음, 런타임 서비스 계정은 버킷 1개와 시크릿 접근 권한만, 그리고 부팅 시 타임스탬프가 찍힌 격리 리포트입니다.
